# 블로그 탐구 글 작성 가이드

## 질문과 답안 (먼저 쓴다)

- 사용자가 준 주제에서 글이 답할 질문 하나를 정한다.
  예: 주제 "MySQL 인덱스" → 질문 "MySQL 인덱스는 어떻게 50만 행에서 몇 번 만에 찾을까"
  - 참고 영상을 여러 편 받았다면 그 영상들의 질문을 아우르는 질문 하나로 잡는다.
- 답안은 6–10개 항목으로 쓴다. 각 항목은 다음 세 가지를 갖춘다.
  - 주장
  - 왜(원리)
  - 근거: 온라인 출처, 계산, 실험 중 무엇으로 보일지
- 질문 밖의 내용(다른 질문에 답하는 것)은 "더 파고들 거리"로 보낸다.

## 본문.md 구조

```markdown
> <한두 문장 요약: 질문에 대한 답>

## 들어가며
<이 질문이 생기는 구체적인 상황.>
<이 글에서 확인할 것을 목록으로 3–5개.>
<실험 환경을 한 번 밝힌다. 예: "실험은 macOS의 Docker에 띄운 MySQL 8.4.13에서 했다.">

## 1. <답안 항목을 장 제목으로>
<무엇 → 왜(원리) → 근거(공식 문서 인용, 계산, 실험) → 그래서>

## 2. …

## 정리: <질문>에 답하면
<누가 이 질문을 물었을 때 답할 말. 5–8줄. 각 줄에 이유가 붙어 있다.>

## 더 파고들 거리
- <범위 밖이라 뺀 주제.>

## 참고자료
- [1] <문서 제목> — <URL>
- [2] …
```

- **본문.md에는 제목 줄(`# 제목`)을 넣지 않는다.** 사용자는 티스토리에 올리고, 티스토리는 제목 칸이 따로 있어서
  본문에 제목이 있으면 두 번 보인다. 본문은 요약 인용문으로 시작한다. 제목(글이 답하는 질문)은 참고자료.md 맨 위와 보고에 적는다.
- 장은 답안 항목 순서를 따른다. 장 하나에 생각 하나만 담는다.
- 분량: 코드 블록과 인용 원문을 뺀 글이 한글 약 5,000–9,000자(읽는 데 10–15분)다. 더 길어지면 범위를 줄인다.
- **쇼츠 영상은 언급하지 않는다.** 참고 영상을 재료로 받았어도 글은 혼자 읽히는 글이다.
  "영상에서는 ~라고 했다" 같은 문장 없이, 정확한 사실만 쓴다.
  참고 영상이 단순화한 곳(영상 REVIEW의 "가장 약한 부분")은 영상을 언급하지 않고 정확한 내용으로 쓴다.

## 문체와 표기

- 평서체로 쓴다("~다", "~까"). 사용자의 학습 노트가 이 문체다.
- 한 문장에는 한 가지만 말한다. 문단은 3–5문장으로 끊는다.
- 기술 용어 표기는 쇼츠 스킬과 같은 규칙이다.
  - 영어: 제품·도구 이름(MySQL, InnoDB), 고유 구성 요소(buffer pool), 명령·키워드(EXPLAIN, BETWEEN),
    고유한 자료구조 이름(B-tree, B+tree), 약어
  - 한글: 한국어로 굳은 말(인덱스, 테이블, 컬럼, 쿼리, 캐시, 해시, 이진 트리, 페이지, 기본 키)
  - 명령 이름을 동사로 쓸 때는 한글로 쓴다: "커밋된다", "롤백한다". 명령 자체를 가리킬 때만 영어로 쓴다: "COMMIT을 실행하면".
  - 영어 용어가 처음 나올 때 필요하면 한글 설명을 괄호로 붙인다. 예: "buffer pool(InnoDB가 쓰는 메모리 캐시)"
- 새 용어는 처음 나올 때 한 문장으로 풀어 준다.

## 근거 표기

본문의 근거는 독자가 직접 확인할 수 있어야 한다. 그래서 **번호는 온라인 출처에만 달고, 계산과 실험은 본문 안에서 직접 보여 준다.**
로컬 파일(`참고자료.md`)을 근거로 가리키지 않는다(`[E1]`, `[C1]`, "참고자료에 적었다" 등).

- **온라인 출처:** 사실 문장 끝에 `[n]`을 달고, 글 끝 참고자료 목록의 `[n]`에 제목과 URL을 적는다.
  같은 출처를 여러 번 쓰면 같은 번호를 다시 쓴다.
  - 공식 문서 문장을 직접 보여 주는 것이 핵심인 곳은 원문을 짧게 인용하고 바로 아래에 번역을 단다.

    ```markdown
    > "InnoDB indexes are B-tree data structures." [2]
    >
    > InnoDB 인덱스는 B-tree 자료구조다.
    ```

- **계산:** 식과 결과를 본문에 그대로 쓴다. 가정이 있으면 함께 쓴다.
  예: "이진 트리는 한 칸에 값이 1개라, 50만 개면 log₂ 500,000 ≈ 18.9, 즉 19층이다."
- **실험:** 돌린 SQL과 결과 중 핵심 줄을 코드 블록으로 바로 보여 준다. 독자가 따라 해 볼 수 있어야 한다.
  데이터를 만드는 SQL처럼 길지만 재현에 필요한 것은 해당 장이나 글 끝 "부록: 실험 재현"에 둔다.

  ````markdown
  인덱스가 없을 때의 실행 계획이다.

  ```sql
  EXPLAIN SELECT * FROM users WHERE email = 'kim@ex.com';
  ```

  ```text
  type: ALL    rows: 497800
  ```
  ````

- 근거를 찾지 못한 주장은 쓰지 않는다. 꼭 필요하면 "공식 문서에서 확인하지 못했다"고 밝힌다.

## 코드, 출력, 그림

- SQL과 명령은 실제로 돌아가는 문법으로 쓴다.
- 명령 출력은 직접 돌린 실험에서 나온 것만 쓴다. 아니면 바로 위에 "예시(실제 출력 아님)"라고 적는다.
  긴 출력은 핵심 줄만 남기고, 줄인 곳은 `…`로 표시한다.
- 표는 써도 된다(비교 결과 등).
- 그림은 코드 블록 안의 텍스트 그림으로 그린다(블로그마다 이미지·mermaid 지원이 달라서). 예:

  ```text
  [루트]          a~j | k~r | s~z
                        │
  [가지]          ka~kh | ki~ko
                          │
  [잎]  … ↔ [kim@ex.com → id 42] ↔ …
  ```

## 참고자료.md 형식 (올리지 않는 작업 노트)

`참고자료.md`는 블로그에 올리지 않는다. 사용자가 글의 사실을 다시 확인하거나 이 글로 영상을 만들 때 쓰는 노트다.
본문이 짧게 보여 준 것의 전체(원문 인용, 계산 과정, 실험 전체 출력)를 여기에 둔다.

```markdown
# 참고자료: <본문 제목>

제목(티스토리 제목 칸에 넣는다): <본문 제목>

블로그에 올리지 않는 작업 노트다. 확인한 날짜: YYYY-MM-DD.
출처 번호는 본문의 [n]과 같다. 계산(C)과 실험(E) 번호는 이 노트 안에서만 쓴다.

## 출처

### [1] <문서 제목>
- URL: <주소>
- 종류: 공식 문서 | 소스 코드·소스 문서 | 보조(개인 블로그 등)
- 본문에서 쓴 곳: <장 번호와 그 문장>
- 원문:
  > "<페이지에서 확인한 문장 그대로>"
- 요지: <한국어로 한두 줄>

## 계산

### C1. <무엇을 계산했나>
- 식과 과정: …
- 가정: …(가정이 바뀌면 결과가 어떻게 달라지는지도)
- 본문에서 쓴 곳: …

## 실험

### E1. <무엇을 확인했나>
- 환경: <날짜, macOS, Docker 버전, `SELECT VERSION();` 결과>
- 재현 방법:
  ```sql
  <돌린 SQL 그대로>
  ```
- 출력(그대로):
  ```text
  <실제 출력>
  ```
- 본문에서 쓴 곳: <장 번호>
```

- 원문은 페이지에서 확인한 문장 그대로 옮긴다. 줄이려면 `…`로 표시한다.
- 같은 페이지의 다른 문장을 여러 곳에 쓰면, 같은 번호 아래에 원문을 여러 개 둔다.
