# content.json 작성 가이드

`content.json` 하나가 대본(나레이션 = 자막), 화면(코드 박스나 다이어그램), 썸네일을 모두 정한다.
`tools/tts.py`, `tools/build.py`, `tools/thumbnail.py`는 이 파일만 읽는다.
완성된 예시: `content.example.json` (Redis 편, 1:59). **형식만 참고한다.** 내용 구성은 아래 원칙에 맞지 않는다(맨 아래 참고).

## 가장 중요한 원칙: 좁게 잡고, 깊게 다룬다

영상을 보고 나면 시청자가 그 주제로 **할 말이 많아야** 한다.
"Docker란 무엇이고 왜 쓸까" 영상을 본 사람이 "Docker가 뭐고 장단점이 뭐예요?"라는 질문을 받았다고 하자.
이름만 대는 수준이 아니라, 이유를 붙여서 여러 가지를 말할 수 있어야 한다.
그러려면 다루는 범위가 좁아야 한다. 넓게 훑으면 항목마다 한 문장밖에 쓸 수 없다.

대본을 쓰기 전에 아래 순서를 지킨다.

1. **질문을 하나 정한다.** 영상을 본 사람이 답할 수 있어야 하는 질문이다.
   - 기본형은 "<주제>가 무엇이고, 장단점은 무엇인가요?"이다.
   - 무엇을 고를지 다루는 주제라면 "언제 A를 쓰고, 언제 B를 쓰나요?"로 한다.
   - 주제에 질문이 여러 개 들어 있을 수 있다(원리 + 사용법 + 비교 + 운영). 그러면 제목이 묻는 핵심 하나만 남긴다.
     나머지는 보고할 때 "다음 영상 후보"로 적는다.
2. **답안을 먼저 쓴다.** 그 질문의 모범 답을 6–8개 항목으로 쓴다(3분 안에 이유까지 들어가는 수). 각 항목은 "주장 + 왜(원리)" 한 쌍이다.
   - 좋은 예: "빠르다. 디스크가 아니라 메모리에서 읽기 때문이다."
   - 나쁜 예: "빠르다"(이유가 없다). "세션, 랭킹, 요청 제한에 쓴다"(이름만 나열했다).
   - 장점만 쓰지 않는다. 단점(한계)도 넣고, 단점마다 "그래서 어떻게 하나"를 붙인다.
   - 답안은 REVIEW.md의 `## 시청 후 답할 수 있는 것`에 그대로 옮긴다.
3. **장면을 짠다.** 답안의 모든 항목이 대본에 **이유와 함께** 나와야 한다. 답안에 없는 내용은 넣지 않는다.
4. **다 쓴 뒤 확인한다.** 답안 항목마다 대본에서 '왜'를 말하는 문장을 찾는다. 없으면 보충하거나 그 항목을 뺀다.

지킬 것:

- 이름만 나오고 왜·어떻게가 없는 항목은 빼거나, 설명할 장면을 따로 준다. "~도 있어요"로 훑고 지나가지 않는다.
- 깊게 다룬다고 어렵게 쓰는 것은 아니다. 시청자는 입문자다.
  - 새 용어는 처음 나올 때 한 문장으로 풀어 준다.
  - 원리는 구체적인 예 하나(코드, 수치, 상황)로 보여 준다.
- 길이가 넘치면 설명(왜)을 줄이지 않는다. 대신 범위(답안 항목)를 줄인다.

## 형식

```json
{
  "voice": "ko-KR-InJoonNeural",
  "rate": "+20%",
  "pronounce": { "MySQL": "마이에스큐엘", "EXPLAIN": "익스플레인", "B-tree": "비트리" },
  "thumbnail": {
    "file": "redis-cli",
    "sub": "# DB가 8초씩 걸릴 때",
    "title": ["<r>Redis</r>,", "왜 쓸까?"]
  },
  "shots": [
    {
      "file": "cache.py",
      "sentences": ["요청이 오면 먼저 레디스를 확인하고, 있으면 바로 돌려줘요.", "..."],
      "blocks": [
        { "at": 0, "lines": ["data = redis.<k>get</k>(<s>\"product:42\"</s>)"] },
        { "at": 1, "lines": ["..."] }
      ],
      "hold": 0.5
    }
  ]
}
```

- `voice`, `rate`: 고정이다. 사용자가 목소리 14개를 비교하고 InJoon +20%로 정했다(2026-10-28). 바꿔 달라고 할 때만 바꾼다.
- `pronounce`: 자막에 영어로 쓴 기술 용어를 나레이션에서 어떻게 읽을지 정한다.
  - `tts.py`가 모든 문장에서 이 용어를 찾아 한글 읽기로 바꾼 뒤 읽힌다. 자막에는 영어가 그대로 나온다.
  - 영상에 나오는 영어 용어는 모두 여기에 한 번씩 적는다. 대소문자까지 같아야 바뀐다.
  - 읽기도 띄어쓰기 단어 수가 같아야 한다. 예: `"Full Table Scan": "풀 테이블 스캔"`(3단어 = 3단어).
- `thumbnail`: 썸네일 이미지 문구. 아래 "썸네일" 절을 본다.
- `shots`: 장면 목록. 장면이 바뀌면 화면이 하드 컷으로 넘어간다.
- `file`: 위쪽 터미널 제목줄.
  - 확장자가 있으면 `❯ cat <file>`, 없으면 명령처럼 `❯ <file>`로 보인다(`incident.log`, `query.sql`, `redis-cli`, `kafka-topics` 등).
  - 장면 내용에 어울리는 파일 이름이나 명령 이름을 고른다.
- `sentences`: 이 장면의 나레이션. 화면 아래 자막에도 이 글자가 그대로 나온다.
  - 영어 용어의 읽기는 보통 `pronounce`로 충분하다. 한 문장만 따로 읽게 하려면 `{"text": "AOF 로그로", "say": "에이오에프 로그로"}`처럼 쓴다.
    `say`가 있으면 그 문장에는 `pronounce`를 적용하지 않는다. 띄어쓰기로 나눈 단어 수가 같아야 한다.
- `blocks`: 코드 박스에 타이핑될 덩어리. 흐름·구조 장면은 대신 `diagram`을 쓴다(아래 "다이어그램 장면" 절).
  - `at`은 몇 번째 문장(0부터)이 시작될 때 타이핑을 시작할지 정한다.
  - 같은 장면의 block은 위에서부터 이어 붙는다.
- `pretyped: true`: 처음부터 타이핑된 상태로 보인다. **첫 장면의 첫 block에만** 쓴다. 영상의 첫 프레임에 내용이 보이게 하기 위해서다.
- `hold`: 장면 끝에서 더 머무는 시간(초). 문장은 짧은데 코드가 많은 장면에 0.5를 준다.
- `markup` 키는 사람이 보는 메모라서 있어도 되고 없어도 된다.

## 길이

- film 120–170초를 목표로 한다. 깊이 다루려면 시간이 필요하므로 3분 한도 안에서 넉넉히 쓴다.
  **3분(180초)은 절대 넘기지 않는다.**
- 이유를 설명하는 문장은 길어서 문장 하나에 약 5초가 든다. 그래서 문장은 약 24–33개, 답안은 6–8개가 들어간다.
  (MySQL 인덱스 편: 처음 39문장은 196초가 나왔고, 33문장으로 줄여 168초가 됐다.)
- `tts.py`가 `narration XX s, film YY s`를 출력한다. film이 170초를 넘으면 아래 순서로 줄이고 다시 실행한다.
  1. 이유를 말하지 않는 연결 문장(예: "그럼 컬럼마다 전부 걸면 될까요?")을 빼거나 다음 문장에 합친다.
  2. 그래도 넘으면 답안 항목을 하나씩 장면째 뺀다. 170초 아래가 될 때까지 반복한다.
  - 남은 항목의 '왜' 문장은 줄이지 않는다.

## 이야기 구조

순서는 답안이 정한다. 기본 뼈대는 이렇다.

1. **훅: 구체적인 사건이나 질문. 2장면을 넘기지 않는다.** 예: "이벤트를 열자마자 상품 페이지가 8초씩 걸리기 시작했어요."
   지어낸 수치는 박스 첫 줄에 `<c># 예시 상황</c>`을 넣어 예시임을 밝힌다.
2. **주제 등장 + 한 줄 정의.** "이럴 때 꺼내는 게 바로, ○○예요." 박스에는 이름만 크게 쓴다(`<r>Redis</r>`). 약어라면 뜻을 풀어 준다.
3. **답안 항목을 하나씩.** 항목마다 1–3장면을 쓴다. 순서는 무엇 → 왜(원리) → 예시(코드·수치·상황) → 그래서.
   - 코드는 실제로 돌아가는 것을 쓴다.
   - 수치는 출처가 분명한 것만 쓰고 "약"을 붙인다. 출처는 REVIEW.md에 적는다.
4. **단점(한계)과 대처.** 장점과 같은 깊이로 다룬다. "단, ~" 한 문장으로 끝내지 않는다.
5. **언제 쓰고 언제 안 쓰나.** 입문자가 직접 고를 수 있게 기준을 준다.
6. **정리.** 답안을 한두 문장으로 묶는다. 시청자가 기억할 한 문장이다.

**"왜 X일까" 주제이거나 앞 영상에서 이어지는 주제일 때**는 뼈대를 이렇게 바꾼다(B-tree 편에서 쓴 방식).
"주제 등장"과 "단점 따로"가 이런 주제에는 어색하기 때문이다.

1. **필요한 앞 내용.** 이어지는 주제일 때만 한두 문장으로 쓴다. 같은 예시(테이블, 값, 클래스)를 다시 써도 된다.
   단, **지난 영상 얘기는 하지 않는다**(사용자 요청). "지난 영상에서 봤듯이", "앞 영상의 save()처럼",
   화면의 `<c># 지난 영상: …</c>` 같은 말을 쓰지 않는다. 이 영상만 본 사람이 알아듣게 그 내용을 직접 설명한다.
   예: "지난 영상에서 봤듯이, 주입된 MemberService는 사실 이 프록시 클래스예요." → "주입된 MemberService는 사실 이 프록시 클래스예요."
2. **질문 장면.** 박스에 질문을 그대로 쓴다. 예: "왜 B-tree? 이진 트리는? 해시는?"
3. **답안 항목을 하나씩.** 대안과 나란히 비교하며 설명한다(이진 트리는 19층, B-tree는 3–4층).
   한계는 장면을 따로 두지 않고, 해당 항목 안에서 대처와 함께 말한다.
4. **정리.**

## 대본(sentences) 규칙

- 해요체 구어로 쓴다. 한 문장은 38자 안쪽이 좋다.
  자막은 쉼표나 마침표에서 나뉘므로, 문장이 길면 나눌 자리에 쉼표를 넣는다.
- **띄어쓰기로 나눈 단어 수와 TTS가 센 단어 수가 같아야** 한다.
  다르면 `tts.py`가 `word count mismatch`를 내고 멈추며, 양쪽 단어 목록을 보여 준다. 그 문장을 고친다.
  - 화살표·슬래시 같은 기호(`→ / ~ ×`)는 대본에 쓰지 않는다. "A/B"는 "A와 B"로 쓴다. "100%를"처럼 단위 기호는 문제없었다.
  - 숫자는 읽히는 대로 쓴다. 예: "약 15만 나노초", "만 명".
  - 숫자 바로 뒤에 동사가 오면 TTS가 두 단어를 하나로 묶을 수 있다. 예: "19번 읽을"이 한 단어로 세어졌다("19층이"는 괜찮았다).
    그러면 그 문장만 `say`에서 숫자를 한글로 풀어 쓴다("열아홉번 읽을"). 자막에는 "19번"이 그대로 나온다.
  - 그래도 어긋나면 `say`로 읽는 문장만 바꿔 단어 수를 맞춘다.
- **기술 용어는 자막에도 영어로 쓴다**(사용자 요청). 자막은 `sentences` 글자 그대로 나오기 때문이다.
  - 영어로 쓰는 것:
    - 제품·도구 이름(`MySQL`, `Redis`, `Docker`, `BullMQ`, `InnoDB`)과 그 고유 구성 요소(`buffer pool`)
    - 명령·키워드(`EXPLAIN`, `SELECT`, `BETWEEN`, `ORDER BY`)
    - 고유한 자료구조·기법 이름(`B-tree`, `B+tree`, `Full Table Scan`), 약어(`DB`, `CPU`, `TTL`)
    - 코드·예시 값(`kim`, `product:42`). 읽기는 `pronounce`에 넣는다(`"kim": "킴"`).
  - 한글로 두는 것: 한국어 문장에서 한글로 굳은 말
    (인덱스, 테이블, 컬럼, 쿼리, 캐시, 서버, 기본 키, 해시, 이진 트리, 배열, 페이지)
    - 명령 이름을 동사로 쓸 때는 한글로 쓴다(사용자가 정했다): "커밋돼요", "커밋하면", "롤백해요".
      명령 자체를 가리킬 때만 영어로 쓴다: "COMMIT을 보내면", "ROLLBACK으로 되돌려요". "COMMIT돼요"처럼 쓰지 않는다.
    - "해시"는 사용자가 정했다. 해시맵·해시 함수처럼 한글로 굳은 말이고, "이진 트리"와 나란히 나올 때 한 줄에 영어와 한글이 섞이지 않는다.
    - 애매하면 "개발자가 한국어로 말할 때 보통 한글로 쓰는가"로 판단한다.
  - 읽는 법은 `pronounce`에 적는다. "마이에스큐엘"처럼 한글 음차를 `sentences`에 쓰지 않는다.
  - 조사는 영어 바로 뒤에 붙이고, 읽는 소리에 맞춘다: "MySQL은"(엘 → 은), "Redis는"(스 → 는).
- 화면 글자를 그대로 읽지 않는다. 나레이션은 설명을 맡고, 화면은 코드·수치·키워드를 맡는다.

## 화면(blocks) 규칙

- 박스는 최대 6줄, 한 줄 최대 약 36칸이다(한글 2칸, 영문·숫자·기호 1칸).
  - 넘치면 글자가 작아진다. `build.py`가 `font down to NNpx`를 출력하면 줄을 줄이거나 장면을 나눈다.
  - 지금까지 가장 빽빽했던 박스는 인덱스 편 insert.sql(약 55px)이다. 원본 크기 프레임에서는 읽혔다.
- 글꼴(D2Coding)은 한글 폭이 영문의 정확히 2배라서, 공백으로 주석 열을 맞출 수 있다.
- 마크업은 중첩할 수 없다.
  - `<k>` 키워드: 분홍
  - `<n>` 숫자·값: 보라
  - `<s>` 문자열: 노랑
  - `<c>` 주석: 회색
  - `<r>` 주제 이름: 빨강
  - 나머지: 흰색
- 대문자 `O`는 숫자 `0`과 헷갈린다. "O/X"처럼 쓰지 말고 말로 쓴다.
- 장면 하나에는 생각 하나만 담는다. 코드 장면은 실제로 돌아가는 문법으로 쓴다.

## 다이어그램(diagram) 장면

장면에 `blocks` 대신 `diagram`을 쓰면, 코드 박스 자리에 상자와 화살표가 그려진다(2026-10-29 추가, 4번 영상에서 사용자가 보고 정했다).
나레이션이 이름을 말하는 순간 그 상자가 나타나고, **지금 말하는 것 하나만 민트 테두리**가 된다. 다음 것이 나오면 원래 색으로 돌아간다.

언제 쓰나:

- 흐름과 구조: 요청이 지나가는 길, 계층(컨트롤러 → 서비스 → 리포지토리), 표준과 구현체, 누가 누구에게 무엇을 보내나, 배포 파이프라인, 정리 장면.
- 코드, 설정, 명령 자체가 예시인 장면은 지금처럼 `blocks`로 쓴다. 문법을 보여 주는 게 목적이기 때문이다.
- 넓게 훑는 영상일수록 다이어그램이 이해를 돕는다. 4번 영상은 20장면 중 12장면을 다이어그램으로 바꿨다.

```json
{
  "file": "flow.txt",
  "sentences": ["JPA는 표준 규칙이고, 실제 일은 구현체인 Hibernate가 해요.", "Hibernate가 만든 SQL을 JDBC로 보내면, ..."],
  "diagram": {
    "rows": [
      [{ "id": "sdj", "text": "Spring Data JPA" }],
      [{ "id": "jpa", "text": "JPA", "kind": "spec", "at": "JPA는", "badge": "표준", "badge_at": "표준",
         "rows": [[{ "id": "hib", "text": "Hibernate", "kind": "impl", "at": "구현체인", "badge": "구현체" }]] }],
      [{ "id": "db", "text": "MySQL", "kind": "db", "at": "DB와" }]
    ],
    "arrows": [
      { "from": "sdj", "to": "jpa" },
      { "from": "hib", "to": "db", "label": "SQL", "at": "SQL을" }
    ],
    "focus": [["hib", "1:Hibernate"]]
  }
}
```

- `rows`: 위에서 아래로 줄을 쌓는다. 한 줄은 항목 배열이고, 줄의 폭을 항목 수만큼 똑같이 나눈다. `null`은 빈 칸이다.
  - 한 줄에 하나뿐인 상자들은 모두 같은 폭이다(가장 긴 글자에 맞추되 줄 폭의 70% 이상).
- 항목:
  - `id`: 화살표와 `focus`가 가리키는 이름. 영어 소문자로 짧게 쓴다.
  - `text`: 상자 글자. blocks와 같은 마크업(`<r>` 등)을 쓸 수 있다. `sub`: 아래 회색 작은 줄(역할 한마디. 예: "HTTP 받기").
  - `kind`: 아래 중 하나.
    - `box`(기본): 회색 테두리
    - `spec`: 노란 점선. 표준(JPA, JDBC)
    - `impl`: 분홍 테두리. 구현체(Hibernate)
    - `db`: 원통. DB와 저장소
    - `text`: 테두리 없는 글자. 열 제목, 요청 줄 같은 것
  - `rows`가 있으면 **틀(frame)**이 된다. 점선 테두리 안에 왼쪽 위 이름표(`text`)를 달고, 그 안에 `rows`를 같은 규칙으로 쌓는다.
    "표준 안에 구현체", "AWS 안의 서비스", "한 프로젝트 안의 두 파일"처럼 포함 관계를 보여 줄 때 쓴다.
  - `badge`: 오른쪽 위 알약 꼬리표. 색은 `kind`를 따른다. `badge_at`이 없으면 상자와 함께 나온다.
  - `w`: 상자 폭(px)을 직접 정한다. 같은 줄에 둔 두 상자 사이에 가로 화살표를 그을 때 쓴다(기본은 칸을 꽉 채워 화살표가 거의 안 보인다).
- `at`: 나타나는 시각. 없으면 처음부터 보인다.
  - `"JPA는"`: 그 단어를 읽기 시작할 때. 대본 단어의 앞부분만 써도 된다(`"Hibernate"` → "Hibernate가").
  - `"1:Hibernate"`: 1번 문장(0부터) 안에서만 찾는다. 같은 단어가 두 문장에 나올 때 쓴다.
  - `1`: 1번 문장이 시작될 때. `"+1.5"`: 장면 시작 후 1.5초. 단어가 없는 곳에 차례로 띄울 때 쓴다.
  - 단어를 못 찾으면 `build.py`가 그 장면과 단어를 말하고 멈춘다.
- `arrows`: `from` → `to`. 상자 가운데를 잇는 직선이고 테두리에서 끊긴다.
  - `at`이 없으면 양 끝 상자가 다 나온 시각에 그어진다. `at`이 있으면 그때 그어지고 민트가 된다(데이터가 지금 흐르는 것).
  - `label`: 세로 화살표는 오른쪽(`"side": "left"`면 왼쪽), 가로 화살표는 위에 붙는다.
    대각선이면 선 위에 얹혀서 상자에 겹치기 쉽다. 라벨이 있는 화살표는 세로나 가로가 되게 배치한다.
- `focus`: `[id, at]` 목록. 이미 보이는 상자를 그 시각에 다시 민트로 만들고 살짝 튕긴다. 나레이션이 앞의 것을 다시 말할 때 쓴다.
- `gap`: 줄 사이 간격(기본 64px). 화살표 길이가 이 간격이다. 줄이 많으면 줄이고, 라벨 자리가 필요하면 늘린다.
- 크기: 판 안 880x810px에 맞춘다. 넘치면 전체가 함께 작아지고, 상자 글자가 40px 아래가 되면 `diagram text down to NNpx`가 나온다.
  그러면 줄 수나 `sub`를 줄인다. 4번 영상에서 `sub`가 있는 상자 5줄은 약 0.95배, 배포 장면(6줄)은 약 0.89배로 줄었고 원본 크기 프레임에서 읽혔다.
- 상자 글자는 이름(영어 용어)과 짧은 역할만 쓴다. 나레이션 문장을 옮겨 적지 않는다.
- 배지가 화살표 끝과 겹칠 수 있다. 화살표가 들어오는 쪽 반대편 칸에 배지 달린 상자를 둔다.

## 썸네일 (thumbnail)

`tools/thumbnail.py`가 이 값으로 `output/thumbnail.png`(1080x1920)를 그린다.
영상과 같은 모습이다(민트 진행 바, 터미널 제목줄, 남색 박스, 민트 커서). 제목은 Pretendard Bold로 크게 쓴다.

- `title`: 큰 글씨 2–3줄.
  - 한 줄은 한글 7자 안팎까지 쓴다.
  - 굵은 영문 한 글자는 한글 한 글자의 약 2/3(소문자)에서 1배(대문자 M·Q 등) 폭이다.
    그래서 `MySQL 인덱스`(141px)가 한 줄의 한계에 가깝다.
  - 넘치면 모든 줄의 글자가 함께 작아지고 `title font down to`가 나온다. 그러면 줄을 짧게 하거나 나눈다.
  - 마크업은 blocks와 같다. 주제 이름은 `<r>`로 쓴다.
- `sub`: 선택이다. 제목 위에 회색으로 나오는 작은 한 줄이다. 코드 주석처럼 `# ...`로 쓰고 상황이나 맥락을 담는다.
- `file`: 위쪽 터미널 제목줄. 장면의 `file`과 같은 규칙이다.
- 문구는 영상이 실제로 답하는 질문(위 1단계에서 정한 질문)을 짧게 줄인 것이어야 한다. 영상에 없는 내용을 약속하지 않는다.
- 영상의 0초 프레임과는 별개다. 0초 프레임은 휴대폰 앱에서 표지를 영상 프레임 중에서 고를 때 쓰인다.

## 예시(Redis 편)를 따라 하면 안 되는 점

Redis 편은 넓고 얕았다.

- 다른 쓰임 3개(세션, 랭킹, 요청 제한)를 장면당 한 문장으로 지나갔다. 왜 레디스가 거기에 맞는지 설명하지 않았다.
- 빠른 이유는 "메모리라서" 하나뿐이었다.
- 메모리가 가득 차면 어떻게 되는지, 캐시와 DB 값이 어긋나면 어떻게 하는지는 다루지 않았다.

새 영상은 이런 나열 대신, 답안 항목 수를 줄이고 항목마다 이유를 끝까지 설명한다.
